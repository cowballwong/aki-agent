# Release notes

## Two audiences, two documents

- **Users** — what is different for them, in their words. What is new, what
  is fixed, what they must do differently. Nothing else.
- **The team** — what changed technically, what to watch, how to roll back.

Writing one document for both produces something neither reads.

## Rules

- Lead with anything that requires action from the reader.
- Name what broke and is now fixed plainly. Softened language about a bug
  people hit reads as evasion.
- Do not list internal refactoring in user notes.

## Include, every time

Version, date, and how to get back to the previous version if this one is
wrong. The rollback line is the one that gets read at the worst moment.
